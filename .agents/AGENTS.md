# Frontend Project Rules

## 1. Package Manager
- Always use **`pnpm`** as the package manager for frontend development.
- Do **NOT** use `npm` or `npx` (e.g., use `pnpm add`, `pnpm dlx`, `pnpm run`).

## 2. API Auto-generation
- The `src/gen` directory is automatically generated by `orval` (`pnpm run gen:api`).
- **DO NOT** write, modify, or add custom code inside `src/gen`.
- Any custom API logic, interceptors, or extensions (like `api-client.ts`) must be placed **outside** of this directory.

## 3. Core Architectural Constraints
- **Styling**: MUST use shadcn tokens (e.g., `bg-background`). NO hard-coded colors.
- **State**: Filter/pagination MUST use TanStack Router search params. NO `useState` for URL state.
- **Forms**: MUST use React Hook Form + Zod. NO manual validation.
- **Dates**: MUST use `Temporal API` (`@/lib/temporal`). Native `Date` is forbidden except at UI boundaries.
- **API**: NEVER call generated API functions directly in components. MUST wrap them in `useQuery`/`useMutation` inside `features/*/hooks/`.
- **Error Handling**: Handled centrally in `api-client.ts`. NO `try-catch` inside components.

## 11. Language Preference & i18n
- **UI Strings**: MUST use `i18n` keys for all user-facing text, notifications, validation errors, and UI strings. DO NOT hardcode raw strings in components.
- **Default Language & Fallback**: Always prioritize English for the fallback/baseline text (e.g., `t("key", { defaultValue: "English text" })`). You do **NOT** need to provide full Vietnamese translations immediately during development; leave them as English fallbacks. We will add the actual Vietnamese translations later when needed.
- **Shared vs Feature**: Use the `common` namespace for shared vocabulary (e.g. actions like Create, Edit, Delete). Use feature-specific locales (e.g. `users.json`) for domain-specific fields.
- **Code comments and logs** CAN be written in **Vietnamese** or **English**.

## 5. Table & Dialog Architecture
- **Data Tables**: Tables must be "dumb" presentation components. Do NOT pass action callbacks (like `onEdit`, `onDelete`) from the parent Page down to the Table. Do NOT place Page headers or "Add" buttons inside the Table component.
- **Action Columns**: Table action columns should directly invoke `useDialogStore(state => state.openDialog)` to open necessary dialogs.
- **Dialog Extraction**: All dialogs (Create, Update, Delete) MUST be standalone components placed in the `features/*/dialogs/` folder and registered globally via the dialog registry (`index.ts`). Do NOT write inline dialog state (`useState`) inside Page components.

## 6. Form Type Safety with Zod Transform
- When a form's API payload structure differs from its UI inputs, handle the mapping using `.transform()` directly within the Zod schema.
- To prevent type mismatches with `react-hook-form`, you MUST use the 3-generic signature for the form hook: `useForm<TInput, any, TOutput>`. Export both `z.input` and `z.output` from the schema file.

## 7. Context-Driven Query State & URL Single Source of Truth
- **Strict Route Schemas:** The TanStack Route schema (`validateSearch`) MUST exactly mirror the Backend API schema (e.g., `zGetUsersQuery`). DO NOT create divergent or simplified schemas.
- **Native Query Objects:** DO NOT `JSON.stringify` complex objects or arrays into query strings. Use TanStack Router's native object serialization capabilities so arrays like `filters` are parsed as real arrays, not strings.
- **DateRange Strict Formatting:** When sending `GreaterThanOrEqual` and `LessThanOrEqual` filters from DateRange pickers, you MUST manually append `T00:00:00Z` and `T23:59:59.999Z` respectively to the date strings to ensure strict UTC bounds.

## 8. Terminal & Background Process Management
- **MANDATORY TERMINAL CONTROL:** Bắt buộc ưu tiên sử dụng terminal (công cụ `run_command` chạy ở foreground) để thực thi các lệnh mà User có thể thấy, điều khiển và dễ dàng tắt. KHÔNG ĐƯỢC để server/tiến trình tự chạy ngầm (background) ngoại trừ trường hợp thực sự cần thiết trong thời gian rất ngắn.
- **CLEAN UP BACKGROUND TASKS:** Nếu bắt buộc phải chạy background task (như `dotnet watch` hay `pnpm dev` để phục vụ tool khác), LUÔN LUÔN phải kill task đó ngay lập tức sau khi dùng xong (bằng lệnh `Stop-Process` hoặc `manage_task kill`). Không bao giờ để lại tiến trình treo ngầm "xả rác" tài nguyên hoặc chặn port khiến User không thể tự chạy code.
- **User Control:** Trả lại hoàn toàn quyền kiểm soát terminal cho User sau khi xác nhận code hoạt động. User sẽ tự chạy server trên IDE của họ để tiện theo dõi log.

## 9. Code Verification
- **TypeScript Check:** LUÔN LUÔN chạy lệnh kiểm tra lỗi type của TypeScript (`pnpm tsc --project tsconfig.app.json --noEmit` hoặc `pnpm tsc -b`) sau khi hoàn thành việc viết code, trước khi báo cáo hoàn thành cho User. Do cấu trúc project Vite sử dụng references, lệnh `pnpm tsc --noEmit` cơ bản sẽ bị pass ảo (không soi vào thư mục src). Bất cứ lỗi TypeScript nào xuất hiện cũng phải được sửa ngay lập tức.

## 10. React Aria Components & Reusability
- **Custom Shadcn Stack:** This project uses a specialized version of Shadcn built on **React Aria Components**, NOT standard Radix UI. Component structures (like Dialog, Select, Checkbox) differ significantly from standard Shadcn documentation.
- **Component Props Constraints:** Because it is NOT Radix UI, standard Radix properties like `asChild` often do **NOT** exist or behave differently. Before using generic Shadcn properties, you MUST read the component's type definition in `src/components/ui/` or check the package readme.
- **Reuse Existing Base Components:** Before creating new UI structures or raw components, you MUST inspect the `src/components/` directory (especially `src/components/custom-ui/` and `src/components/layout/`) to reuse existing robust components (e.g., `BaseDialog`, `BaseFormDialog`, `ResourcePageShell`, `FormSubmitButton`). Do not reinvent standard dialogs or page shells.
- **CodeGraph Usage:** It is highly encouraged to use the `codegraph_explore` MCP tool (or `codegraph explore` shell command) to quickly understand how existing custom components are constructed and utilized in the codebase. This ensures architectural consistency.

## 13. Dynamic Form & Form Control Architecture
- **Phân biệt Thuật Ngữ**: Luôn sử dụng `FormRenderer` (vẽ Form cho End-User từ JSON) và `FormBuilder` (Giao diện cấu hình cho Admin).
- **Zod Validation**: Các giới hạn logic như `min`, `max` (cho số) bắt buộc phải cấu hình bằng Zod schema (`z.number().min()`), TUYỆT ĐỐI KHÔNG cấu hình qua HTML prop trong form động vì các component như `react-number-format` render ra thẻ `<input type="text">` và sẽ bỏ qua HTML min/max.
- **BaseFormField Config**: Mọi Form Control phải bọc qua `BaseFormField` và dùng `OmitFormProps` để tránh xung đột Type với React Hook Form. Thuộc tính `config` sinh ra để chứa các HTML prop native (như `maxLength`) và prop riêng của component.

## 14. Feature Analysis & UI Layout Heuristics
- **Simple Entity Features:** When a feature request only involves 1 single entity, has very few fields, and at most 1 foreign key, assume a standard **Table layout** (ResourcePageShell / BaseTable) at Frontend. Do not ask redundant questions about UI layout.
- **Complex Features:** When a feature request is complex, involves multiple fields, multiple entities, or complex scene data flows, YOU MUST proactively ask the user to clarify: (1) Preferred UI layout (List Card, Canvas, Dashboard, Tabbed View, etc.), (2) Field mapping to dedicated Command/Query & Response DTOs, and (3) Scene Data Flow design to minimize API roundtrips.
